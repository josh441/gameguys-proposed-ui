What changes

Four adjustments, no new screens.
  • +
    One engine. Lead-time cover folds into this query and the separate auto-PO page stops writing POs, so the quantity reviewed is the quantity ordered. Today it writes the un-adjusted baseline instead.
  • +
    Snoozes respected. A row deferred with a reason no longer reappears here. The board currently ignores them.
  • +
    Truncation visible. "24 suggestions, showing 8" instead of silently cutting the list at 10.
  • +
    Every row ends with an outcome. Ordered, passed, unavailable and substituted, or snoozed. Nothing leaves the round undecided.

What an offer unlocks

Built on the document extractor and the alias table that already exist.
On the buy list
An availability chip per suggestion, the best-price supplier when more than one replied, and ranked alternates when the exact SKU is out.
On the PO
Line costs prefilled from the accepted offer instead of a default cost, so a promoted line is never a zero-cost placeholder.
Over time
Supplier fill rate from promised versus allocated versus received, which is the scorecard two code comments already reference and no table implements.

Two fixes worth more than the card

  • 1
    Approval can currently be skipped. The status setter validates the target status but never reads the current one, so draft to ordered goes straight through and never reaches the admin-only gate. A real transition table closes it.
  • 2
    Nobody is recorded as the approver. There is no approved_by column, so identity survives only in the activity log. A separate approver column is hardcoded to a name on the create form and stays editable elsewhere, reconciled against nothing.
Optional, owner's call. Standing authority: named supplier, restock only, under a set amount, auto-approved with a daily digest that can be reversed. Default off. It is the only real fix for single-approver latency, and it is a policy choice rather than a build task.

Why arrivals are unreliable today

Four separate causes, all cheap to fix.
  • 1
    The real ETA drives nothing. The carrier webhook writes an ETA on every update and the PO detail page shows it. Nothing else uses it: not the board lanes, not the late calculation, not the dashboard, and not as a fallback when the typed date is missing.
  • 2
    Late tracking is never registered. Registration fires only on the transition to ordered. A tracking number added afterwards, including from the receive page, never gets a status or an ETA. Changing a tracking number blocks re-registration permanently.
  • 3
    The late badge skips paid POs. Overdue requires payment to be empty, but payment is a hard gate before receiving, so nearly every PO actually in transit is already paid and shows no badge.
  • 4
    Exceptions notify nobody. The webhook writes the exception tag. There is no branch on it and no message goes anywhere.
